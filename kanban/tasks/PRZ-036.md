## Evidence
<!-- Wypełnia wykonawca przed `review`: realne wyjście komend, opis weryfikacji. -->

Zmiana jednego pliku: `app/static/css/app.css`. Selektor `.formula .op` był **martwy** —
żaden element w HTML-u nie ma klasy `op`, bo `app.logic.formula.to_html` nadaje każdemu
spójnikowi własną, stałą klasę. Zamiast niego arkusz zna teraz pięć klas z umowy
`docs/ARCHITEKTURA.md:140`: `.formula .op-neg`, `.formula .op-and`, `.formula .op-or`,
`.formula .op-imp`, `.formula .op-iff`. Deklaracje zostały bez zmian
(`padding: 0 0.15em; color: var(--kolor-akcent)`), więc wygląd spójników, który wcześniej
nie działał wcale, jest teraz taki, jaki zakładał PRZ-008. Wszystkie 42 wystąpienia
`formula_to_html` w szablonach są owinięte w element z klasą `formula`, więc zawężenie do
`.formula` nadal obejmuje każdy wzór.

### 1. Klasy wypisane przez `to_html` a reguły w arkuszu

Dla formuły z wszystkimi pięcioma spójnikami wypisuję klasy z `to_html` i sprawdzam, że
każda ma w arkuszu własny selektor:

```
$ for k in $(uv run python -c "from app.logic import formula as f; import re; print('\n'.join(sorted(set(re.findall(r'op-[a-z]+', f.to_html(f.parse('∼p ∧ q ∨ r → s ≡ t')))))))"); do if grep -q "\.formula \.$k\b" app/static/css/app.css; then echo "OK  .formula .$k -> jest w app.css"; else echo "BRAK .formula .$k"; fi; done
OK  .formula .op-and -> jest w app.css
OK  .formula .op-iff -> jest w app.css
OK  .formula .op-imp -> jest w app.css
OK  .formula .op-neg -> jest w app.css
OK  .formula .op-or -> jest w app.css
```
